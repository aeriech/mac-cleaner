# Design: Disk Detective (answer "why did my disk fill up?")

Generated by /office-hours on 2026-10-29
Branch: main
Repo: aeriech/mac-cleaner
Status: DRAFT
Mode: Builder

## Problem Statement

Everyday Mac users who see "storage almost full" can't tell what filled their disk, or whether it's safe to remove. macOS lumps most of it into "System Data", which forum users describe as 100–500 GB with no obvious way to see what it is, and they distrust cleaner apps that delete things without explaining them.

Real case, on the maintainer's own Mac (2026-10-29): free space fell 27 GB in a week. Finding the cause took about an hour of manual `du` runs and a Full Disk Access detour: Telegram's media cache had grown to 35 GB, 34 GB of it downloaded in the previous 7 days. Separately, Microsoft Teams and Polly Teach, deleted months earlier, had left about 730 MB behind, and Mac Cleaner's Leftovers rules first judged them wrongly.

Mac Cleaner keeps no memory between scans today (verified: no persistence anywhere in `Sources/`), so every question starts from zero.

## What Makes This Cool

Mac Cleaner becomes a detective, not a broom. On launch it says **"+41 GB added this week, mostly Telegram"**. After a week it says **"At this rate, your disk is full by Nov 12"**. It labels leftovers with proof: **"Microsoft Teams, installed until Jun 4"**. No free Mac tool tracks growth per app over time; visualizers (GrandPerspective, DaisyDisk) only show today's snapshot.

## Constraints

- **Audience:** everyday Mac users with a full disk, not developers first (session decision D2).
- **No paid Apple Developer ID yet** ("decide later", D3): nothing may depend on notarization, and there's no new background helper or login item by default (macOS shows a "background item added" notice, which costs trust).
- **Local only:** the scan history never leaves the Mac; no network calls.
- **Toolchain:** Swift Command Line Tools only (no `@State` macro); tests are standalone executables in `Tools/*.test.swift`.

## Premises (agreed)

1. The target user wants **answers** (what is System Data, what grew, who owns it) before buttons.
2. **Trust is the product:** nothing deletes what it can't explain; uncertain items stay unticked; removals stay reversible or are clearly labelled permanent.
3. The gap versus other tools is **time**: what was added this week (visible on first launch), what changed since last week, and leftovers proven by Mac Cleaner's own memory of installed apps. *(Revised after the second opinion: replaces "catch leftovers with a Trash watcher".)*
4. Install friction is a known open risk; features must not depend on paid signing or make install harder.
5. Doing nothing isn't neutral: without memory, every user repeats the hour-long hunt.

## Cross-Model Perspective (Claude subagent, cold read)

- **Coolest version:** a disk-full forecast that names the culprit, plus "stop it growing" guides, because clearing Telegram's cache is a treadmill if Telegram keeps downloading 5 GB a day. The seed exists: `appDataHints` in `Sources/AppData.swift`.
- **What it read as the core:** the user's own words, "i dont know if it really needs it": they want a verdict with evidence, not a delete button. The Teams case ("is this really left over or im wrong") showed memory beating heuristics.
- **Existing tools:** nothing open source tracks per-app growth; this repo already has the hard part (folder → bundle ID → app name in `scanAppData`). Pearcleaner reportedly has a Trash watcher (not verified, license unverified), so a Trash watcher wouldn't set Mac Cleaner apart.
- **First-launch value:** "added in the last 7 days" from file creation dates works before any history exists.
- **Trust bug (verified):** `README.md` line 11 promises "Anything it removes goes to the Trash first", but Smart Clean (`SmartClean.swift:119`) and App Data (`AppData.swift:155`) delete permanently.

## Approaches Considered

- **A: "This week" on App Data** (no saved history). Became Milestone 1 of B.
- **B: Disk Detective with scan history.** Chosen.
- **C: "Stop it growing" coach.** Folded into B as Milestone 3 rather than standalone, because it needs B's growth numbers to know when to show a guide.
- **Rejected:** a Trash watcher for leftovers. It duplicates Pearcleaner, misses apps deleted from Launchpad, and needs a background helper.

## Recommended Approach

Approach B, built in four milestones. Wireframe: `.gstack/sketch/disk-detective-wireframe.png` (approved).

**M0: Trust fix (first, ~10 min).** Rewrite README line 11 to say what actually happens: Uninstaller, Leftovers, Large Files, Duplicates and Similar Images move items to the Trash; Smart Clean and App Data delete caches permanently, because moving a cache to the Trash frees no space. Decision: keep permanent deletion for caches, since Trash-first would defeat the purpose for a full disk.

**M1: "Added this week" (no saved history).**
- `recentBytes(path, days: 7)`: enumerate files with `.creationDateKey`, `.totalFileAllocatedSizeKey` and `.isRegularFileKey`, sum those created after the cutoff, with an autorelease pool per file (lesson from QA ISSUE-001).
- Add `recent: Int64` to `AppDataEntry`, filled in `scanAppData` next to `diskUsage`.
- App Data hero: "+X GB added this week, mostly <app> (<what it is>)", with "Grew this week" as the default sort and "Biggest" as the alternative.
- Label it **"added"**, not "grew", because it counts new files only and ignores deletions.
- Empty state: "Nothing grew much this week. Your disk is stable."
- Test in `Tools/AppData.test.swift`: two files, one with `creationDate` set back 30 days; `recent` equals the newer file's size.

**M2: Scan history, net change, forecast, proven leftovers.**
- **History file:** `~/Library/Application Support/Mac Cleaner/history.jsonl`, one JSON line per App Data scan: `{v: 1, date, free, total, installed: [{id, name}], sizes: {<app folder>: bytes}}`. Keep at most 365 records and drop the oldest; skip writing if the last record is under an hour old.
- **Net change:** diff against the newest record at least 6 days old; show "+34 GB since last Thursday" per app and the free-space change.
- **Forecast:** only with at least 2 records spanning 3+ days and free space falling. Full date = today + free space ÷ average daily decline. Hide it when free space is stable or rising.
- **Proven leftovers:** a bundle ID present in an earlier record's `installed` list but missing now is a fact. Show the app's human name from that record, a "Proven" badge and "installed until <last seen>", ticked by default. Older leftovers keep today's rules ("Check first").
- **Clear history** button on App Data; history is local only.
- **Tests:** append and parse; 365-record cap; forecast maths (falling, stable and rising cases); proven leftover from a fixture history.

**M3: "Stop it growing" guides.**
- Grow `appDataHints` into structured guides (title, steps, "verified for <app version>") for apps users actually hit: Telegram, Docker, iPhone backups, Xcode, Slack, WhatsApp, Spotify, Teams.
- Show a guide when an app added over 1 GB this week.
- Each guide is checked against the real app before it ships; a wrong instruction costs more trust than none.

## Open Questions

- Besides the App Data hero, should the forecast also appear in the sidebar's disk meter?
- Should the history also record free space on every app launch (no background helper), so the forecast sharpens even when App Data isn't scanned?
- Should "Proven" leftovers be ticked by default? (Proposed: yes; they go to the Trash.)
- Developer ID / notarization (deferred, D3) remains the biggest risk to reaching everyday users.

## Success Criteria

- On the maintainer's Mac, the first App Data scan shows Telegram's weekly additions at the top; the hour-long hunt becomes one glance.
- After two scans at least 6 days apart, App Data shows net change per app and either a forecast date or "stable".
- An app deleted between two scans appears in Leftovers as "Proven", with its human name and last-seen date.
- No new background item or login item; nothing leaves the Mac; all existing tests plus the new ones pass.
- The README no longer overclaims.

## Distribution Plan

Unchanged: GitHub Releases zip (Apple silicon) and build-from-source via `./build.sh --install`. Notarization, a Homebrew cask and an Intel/universal build are deferred (D3) and remain the main reach risk for the everyday-user audience.

## The Assignment

Today, open Telegram and set its cache limit (Settings → Data and Storage → Storage Usage, or wherever your version puts it). Write down the exact menu path and Telegram's version number; that becomes the first verified "stop it growing" guide. Then note today's free space and Telegram's size in App Data, and check both again in 3 days. If Telegram still grows more than 2 GB, the guide is wrong, and you'll know before shipping it.
